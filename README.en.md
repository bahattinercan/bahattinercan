## In short

I have been writing code since 2019, with 4+ years of professional experience. I build REST APIs,
JWT authentication and role-based authorization with **Django and Django REST Framework**; service
layers with **Node.js/Express**; and cross-platform iOS and Android apps from a single **Flutter**
codebase.

On the web I build interfaces with React, Next.js and Angular; on the game side I have developed
and published hypercasual mobile games with Unity and C#. Database schema, migrations and Docker
deployment are the shared foundation across all four areas.

English **C1** · open to remote work abroad and on-site roles in Türkiye · available immediately.

## How I work

### Tests

I do not start tests where most people start them. A crashed screen announces itself and usually
gets fixed the same day; the real problem is code that never throws but returns the wrong answer.
That is why most of the 725 tests in Customer Order Tracking exist: partial payments, balances,
production stage transitions. 535 in the Beauty Salon platform, 101 in Taskbar Hero, 68 test files
in the maintenance system. I do not treat a test count as an achievement in itself; what it buys me
is not being afraid when I change something.

### Data model

When I start a project I think about the data before the screen, because the data model outlives the
code. In Customer Order Tracking, the answer to "is it paid" is not a field on the order: the
payment hangs off the collection and the balance is a derived value. A single "paid" flag would have
been easier, but with three-part payments that flag lies. In multi-tenant systems the tenant id is
not a silent assumption; it is a required parameter on every cross-module call.

### Backend and API

I do not tie business rules to HTTP. In the maintenance system every module is split into
application / domain / infrastructure, and the domain layer is plain TypeScript: no Nest, no Prisma,
no HTTP imports. The same service is called from the API and from the queue consumer. Those layer
rules are checked by dependency-cruiser, so the rule does not rot in a document. A module exposes
exactly one `index.ts`; I do not write directly into another module's repository or table. I do not
hand-write the client: it is generated from the API's OpenAPI output, so a renamed field cannot
leave the client quietly stale.

### Interface

React, Next.js and Angular on the web, Flutter on mobile; the decisions stay the same. Empty,
loading and error states are part of the screen, not something bolted on later. I do not fix
responsiveness at the end; I build it so it does not break at 360 px from day one. Flutter gives me
iOS and Android from one codebase; I separate the parts that behave platform-specifically and keep
the rest shared.

### Games

On the game side, measurability comes before visuals for me. In Taskbar Hero the combat engine is
pure Kotlin, fully separate from the UI, and the simulation is fixed-step. The same seed produces
the same result, so I compare a balance change with a JVM test instead of a guess, without opening a
device or emulator. On Unity I worked on levels, mechanics, physics and control systems in
hypercasual games; 23 prototypes are in `unity-prototypes-archive`.

### Decisions and documentation

I do not keep decisions in my head, I leave them in the repo; six months later I will not remember
why I did something either. I also write down what I decided not to do, because the real argument
starts with "why did you not build this" and without a written answer it restarts every month.
READMEs do not praise the architecture, they describe the boundaries: what lives where, and what
must not move in.

### Deployment and environments

Development, test and production are separate. Seeding production with the default password is
closed off in code; writing the rule down is not enough, because the person reading the rule is also
the person in a hurry that day. I use Docker for deployment, treat migrations as part of the deploy
and keep secrets out of the repo. Nothing gets merged before tests and type checks pass.

### Working in a team

What helps most in a team is not how fast you write code but whether the work can be handed over;
when I finish something the question I ask is not "does it run" but "does it run without me". I send
small, single-purpose changes for review, because a PR holding two jobs does not get read and takes
both down when it has to be reverted. I put the comment on the code, not the person: "what happens
in this case" gets an answer, "why did you do it like that" does not.

I automate style arguments: with a formatter, a linter, type checks and tests running in CI there is
nothing left to debate. When a decision I disagreed with is made, I state my reason once and then
build it, and I write the objection down; a verbal objection turns into "I told you so" three months
later and helps nobody. When I explain something to someone new I do not just show the fix, I say
why, so the next similar case does not need a question.

### Delivery and scope

Instead of arriving with one big delivery I start with a small slice that works end to end, then
build on it. When I am unsure I ask; guessing at scope and priority especially tends to cost more
later. If I suggest not building something, I give the reason rather than just saying no.
